# RSS媒体阅读器

一个轻量级本地 RSS 媒体阅读器，适合个人自用。前端为纯静态页面（浏览器直接运行），后端代理由 Cloudflare Pages Functions 提供。支持添加 RSS 订阅源、聚合展示图文 / 视频内容、收藏、搜索、已读隐藏、订阅导入导出，以及针对部分国外媒体资源的代理播放。

当前版本：`5.2 稳定版`
（5.2：hls.js 升级到 1.7.3；日志顶部新增「代理在线状态 + 出口 IP + 接入节点城市/国家」；今日更新改为按时间逐次列举（条目/已读/未读/屏蔽/隐藏/失败）；存储读数只保留「可浏览条目」）
（5.1：文章缓存上限调为 1000；运行日志改为「仅当天 + 直接显示 + 三按钮」；新增 hls.js 版本提醒）

## 功能特点

- 本地添加和管理 RSS 订阅源
- 支持图片类 RSS 和视频类 RSS
- 支持一键导入、导出订阅源 JSON
- 首页聚合展示所有订阅内容，并按发布时间从新到旧排列
- 支持图片宫格展示和大图预览（滑动切换）
- 支持 MP4 视频播放
- 支持 m3u8 视频播放，基于 HLS.js
- MP4 和 m3u8 使用统一的自定义控制栏（播放 / 暂停、进度条、缓冲指示、剩余时长、静音、全屏）
- 支持收藏内容
- 支持关键词搜索标题
- 支持已读隐藏，避免下次打开重复显示已读内容
- 支持本地文章缓存，二次打开可先显示上次内容
- 支持 RSS 分批加载，减少大量订阅源同时请求造成的卡顿
- 支持推特 / X / twimg 等指定域名媒体资源代理
- 视频缓冲自愈：HLS 致命错误自动恢复，显著降低"播放几秒自动暂停 / 有时长不播"的概率
- **运行日志（5.0 新增，5.1 改版，5.2 增强）**：底部新增「日志」标签页，只记录**当天**运行情况（跨天 00:00 自动删除旧报告）。页面顶部显示**代理是否在线 + 本机公网 IP + 接入的 Cloudflare 节点城市/国家**；下方按时间**逐次列举**今天的每一次刷新（条目 / 已读 / 未读 / 屏蔽 / 隐藏 / 失败），再列出全部错误记录；顶部提供「删除报告 / 复制报告 / 导出报告」三个按钮

## 使用方式

直接打开 `index.html` 即可使用（需配合部署后的 Functions 代理才能播放被墙的媒体资源）。

如果部署到 Cloudflare Pages、GitHub Pages 或其他静态网页服务，也可以直接访问部署后的页面。本项目使用 Cloudflare Pages Functions 作为 RSS 拉取与媒体代理后端，需绑定 Cloudflare 账号并配置 Pages 项目。

首次使用时，在"添加订阅"页面粘贴 RSS 地址，然后选择订阅类型：

- 图片类 RSS
- 视频类 RSS

添加后切换到主页，阅读器会自动加载订阅内容。

## 数据保存

本项目默认使用浏览器本地存储，不依赖账号系统。

本地保存的数据包括：

- RSS 订阅源
- 收藏内容
- 已读记录
- 最近一次成功加载的文章缓存
- 最近一次刷新时间

这些数据保存在当前浏览器中。如果更换浏览器、清除浏览器数据或换设备，数据不会自动同步。

## 代理说明

项目内将 RSS 拉取代理和媒体资源代理分开处理。

RSS 代理入口：

```js
const RSS_PROXY_ENDPOINTS = [
    "https://rss-twitter-viewer.pages.dev/rss-proxy",
    "https://rss-twitter-viewer.pages.dev/proxy"
];
```

媒体代理入口：

```js
const MEDIA_PROXY_ENDPOINT = "https://rss-twitter-viewer.pages.dev/media-proxy";
```

默认需要代理的域名（内置，代码写死、UI 中只读）包括 twitter/x/twimg 系、xcancel、niter、redgifs、rsshub.app、phe69、htumeng.com、btumeng.com 等。

> **新增代理域名的正确做法（当前版本无 UI 可编辑）**：必须**同时**修改以下三处、保持完全一致，缺一处就会出现「前端判定直连→跨域失败」或「代理层 403 拒绝」：
> 1. `js/core.js` 的 `FORCE_PROXY_HOSTS`（决定前端走代理还是直连）
> 2. `functions/rss-proxy.js` 的 `BUILTIN_RSS_HOSTS`（RSS 代理服务端白名单）
> 3. `functions/media-proxy.js` 的 `ALLOW_PROXY_HOSTS`（媒体代理服务端白名单）
>
> 当前版本的 `rss-proxy.js` 只认内置白名单，**不读取 KV 用户名单**（`proxy_rss_user`），因此靠写入 KV 无法让新域名生效。下面描述的「代理域名」按钮在**本仓库当前版本中尚未实现**，仅作后续规划。

**扩展代理域名不再需要改代码**：在阅读器底部【管理订阅】与【收藏】之间的「代理域名」按钮，打开的是与「收藏 / 添加订阅」一致的全屏管理页（RSS 代理 与 媒体代理 两区之间用绿色分隔线隔开，按钮统一蓝色），可分别给 **RSS 代理** 和 **媒体代理** 增删域名，点「保存并同步」即写入后端 KV（`RSS_CACHE` 命名空间下的 `proxy_rss_user` / `proxy_media_user` 键），前后端自动生效。

> 安全：写入接口 `/proxy-config` 需要管理令牌，令牌在服务端环境变量 `PROXY_ADMIN_TOKEN` 中设置，界面里输入的令牌须与它一致；未设置则拒绝写入，防止被当开放代理滥用。

普通国内图片、MP4、m3u8 链接会优先由浏览器直接加载。匹配到上述域名的媒体链接会通过 `media-proxy` 代理。

Twitter 订阅通过 Nitter 实例（asia.aguea.com）获取推文内容，媒体链接自动替换为 Twitter 官方 CDN 域名（`pbs.twimg.com`、`video.twimg.com`），通过代理加载以获得更快的速度。

### 代理域名（5.0 更新）

Twitter 订阅的 RSS 地址现在**固定使用官方 Pages 域名** `https://rss-twitter-viewer.pages.dev`，不再依赖访问时所在的域名。此前曾用 `location.origin` 拼接，若经自定义域名（如 `mypear.ccwu.cc`）访问，生成的 Twitter RSS 订阅地址也会指向该自定义域名；当该自定义域名在手机端失效时，所有 Twitter 订阅将无法加载。固定为官方域名后，无论以哪个域名进入应用，订阅地址始终可用。媒体 / RSS 代理端点（`RSS_PROXY_ENDPOINTS`、`MEDIA_PROXY_ENDPOINT`）本身也始终指向 `rss-twitter-viewer.pages.dev`。

## m3u8 播放说明

m3u8 视频使用 HLS.js 播放，已针对代理视频场景优化：

- 关闭低延迟模式（`lowLatencyMode: false`），使用标准点播缓冲策略
- 缓冲长度 `maxBufferLength: 60` 秒，回退缓冲 `backBufferLength: 30` 秒。跨境 / 弱网场景下前向缓冲余量越大越抗抖动，故保留 60 秒（曾下调至 30 秒，实测弱网更易卡顿，已回调）
- 自适应码率从低级别开始（`startLevel: -1`），快速起播避免黑屏
- 根据播放器尺寸自动限制最高分辨率（`capLevelToPlayerSize: true`，最高 720p），避免高码率拖垮弱网
- **致命错误自愈**：NETWORK_ERROR 自动 `startLoad()`、MEDIA_ERROR 自动 `recoverMediaError()`，最多重试 3 次，显著降低"播几秒自动暂停 / 有时长不播"的概率
- **缓冲遮罩**：加载等待时显示半透明"缓冲中"提示，区分"正在缓冲"与"真卡死"
- 代理视频采用两次点击模式：第一次加载 manifest，第二次点击播放

## 布局与适配

- 移动端**单列**布局，卡片宽度自适应，无双列瀑布流
- 折叠屏展开态也以单列呈现，避免"左侧优先加载"带来的割裂感与卡片乱跳
- 顶部 / 底部悬浮栏为磨砂玻璃固定栏，普通手机上自动贴合屏幕边缘

## 运行日志（5.2：仅今日 · 直接显示 · 顶部带代理状态）

底部导航在「收藏」右侧新增第六个「日志」按钮，点击进入全屏独立标签页。

- **只记当天，00:00 自动删除**：日志只保留当天一份（key `rsslog:YYYY-MM-DD`）。跨入新的一天时（每分钟检测 + 每次打开页面时）会把除今天以外的所有报告**直接删除**，因此不会有历史列表，也不占长期空间。
- **直接显示，无列表 / 无弹窗**：进入日志页即直接展示今日内容，自上而下为：
  - **顶部「代理 / 网络状态」卡片（5.2 新增，见下节）**：`代理在线 ｜ 接入节点 洛杉矶 LAX · 美国` + `本机公网 IP … ｜ 识别地区 中国（CN）`。
  - **一、今日更新（共 N 次）**：**按时间逐次列举每一次刷新**，每条为
    `[HH:MM:SS] · 来源` + `条目 A ｜ 已读 B ｜ 未读 C ｜ 屏蔽 D ｜ 隐藏 E ｜ 失败 F`，**所有数字蓝色加粗**。
    - `条目` = 本次刷新后本地缓存中的可浏览条目数；`已读 / 未读` 以「已读链接集合」划分。
    - `屏蔽` = 命中屏蔽关键字的条目数；`隐藏` = 被隐藏的纯文字推特条目数（无图/无视频/无 iframe）。两者均为说明性统计，不影响列表渲染。
    - `失败` = 本次刷新中加载失败的订阅源个数。
    - 若本地完整存下则不额外显示；**仅在配额降档时**追加红字 `（本地只存下 N 条，已被配额降档）`。
    - （5.1 时这里只显示「最近一次 + 累计次数」一行，5.2 改为逐次列举，便于回看一天内的变化过程。）
  - **二、错误记录（前台 / 后台）**：每条含时间、来源（如 `RSS加载`、`媒体`、`前台`、`启动期`）、错误内容。**媒体类错误额外带上「订阅来源 + 真实域名 + 状态码 + 地址」**（例：`HLS播放失败：源【图萌社】域名 cdn.xxx.com 状态403 地址 https://...`）；同一「来源+域名」15 秒内去重一条。
  - **三、提示**：当前为 **hls.js 版本检查**（见下节）。
- **顶部三个按钮**：`删除报告`（删除今日报告并从零重新累计，二次确认）、`复制报告`（复制今日报告的纯文本）、`导出报告`（把今日报告导出为 JSON 文件，文件名 `运行日志_YYYY-MM-DD.json`）。复制 / 导出的文本同样包含顶部代理状态与逐次更新明细。
- **本地存储读数**（读数条常驻，进入日志页即刷新）：
  1. `可浏览条目 N 条 / 体积` —— `rss_article_cache` 的真实条数，**这就是「你在软件里实际能翻到的条目数」**（主页 / 收藏 / 搜索都取自这一份，上限由 `ARTICLE_CACHE_LIMIT` 决定，当前 1000）；若低于上限会红字提示「可能已被配额降档」。
  2. `本地存储已用 A / 上限约 5 MB（NN%）` —— **决定会不会降档的就是这一条**。按占用率变色：<70% 灰、70–90% 黄、≥90% 红并提示先清理报告。
  3. `本站占用 A ｜ 本域名全部键 B` —— 判断是否被同域其它脚本挤占。

  读数的体积按 UTF-16 计（1 字符 = 2 字节）。早期版本曾在此并列显示 `navigator.storage.estimate().quota`（约 142 GB 的「大容量配额」），那是 **IndexedDB / Cache / OPFS 那一层的配额、与 localStorage 毫无关系**，会误导成「还能存 142 GB」，已移除。
  **5.2 另删除了一行 `来源缓存 X 个源 ｜ 合计 N 条`**：各订阅源的原始回退副本（仅在某源请求失败时用于离线兜底）**不进列表、不代表任何可浏览内容**，与第 1 行的「可浏览条目」根本不是同一份数据，两个数字并列只会造成「到底能看 1000 条还是 899 条」的困惑，故整行移除。该数据仍可通过 `AppLog.measureStorage()` 取到（`rssFeedCount` / `rssItemCount`）。
- **数据存储**：报告存于浏览器 `localStorage`（键名 `rsslog:YYYY-MM-DD`），不依赖账号，仅本机可见。

### 顶部「代理 / 网络状态」（5.2 新增）

| 显示项 | 含义 |
|---|---|
| `代理在线` / `代理异常` / `代理离线` | 见下方判定规则 |
| `接入节点 洛杉矶 LAX · 美国` | 请求落地的 **Cloudflare 边缘节点**（`colo` 机场三字码，前端用一张 IATA 表翻成城市/国家）——这就是「代理所在的城市/国家」。国内运营商（尤其中国移动）常被调度到美西节点（LAX / SEA） |
| `本机公网 IP 2409:…（IPv6）` | Cloudflare 看到的**访客公网 IP**，也就是本机出口 IP。⚠️ 这**不是**代理服务器的 IP —— 本应用直连 Cloudflare，中间没有别的代理层 |
| `识别地区 中国（CN）` | Cloudflare 按 IP 判断的访客国家/地区代码（如 `CN` / `US`），括号内为原代码，便于和节点所在国对比（例：`识别地区 中国（CN）` 但 `接入节点 洛杉矶 · 美国`，说明流量被绕到了美西） |

**判定规则**（`js/log.js` 的 `checkConn`）：

| 状态 | 条件 | 含义 |
|---|---|---|
| `代理在线` | `GET /ping` 返回 JSON 且 `ok:true` | 代理函数正常运行（最强证据） |
| `代理在线`（灰字注明「/ping 接口未部署」） | `/ping` 返回的是网页（Pages 对未部署路径会回落成 `index.html`），但 `/cdn-cgi/trace` 成功 | 站点可达；只是 `functions/ping.js` 还没推上去，**不代表代理坏了**，节点数据取自边缘 |
| `代理异常` | `/ping` 失败（非回落）且 `/cdn-cgi/trace` 成功 | 站点可达、但 Pages Functions 未按预期响应——仍能拿到 IP / 节点 |
| `代理离线` | 两者都失败 | 连不上 Cloudflare，需检查网络 |

实现要点：

- 数据来源都是**同源地址**，不经过任何第三方：
  1. `GET /ping` —— `functions/ping.js`，由 **Pages Functions 执行**，返回 `{ ip, colo, country, city, asn, ts }`。能答上就说明**代理函数本身在跑**。
  2. `GET /cdn-cgi/trace` —— Cloudflare 边缘直接吐出的纯文本（`ip=… / colo=… / loc=…`），**不经过 Functions**，只能证明「站点可达」，作为降级数据源。
- **每 10 分钟至多检测一次**，结果写进当天报告（`r.conn`），反复切页不会重复发请求；检测失败**不写入错误记录**（属网络环境正常波动）。
- ⚠️ 注意一个 Cloudflare Pages 特性：**访问未部署的路径不会 404，而是回落渲染 `index.html`（HTTP 200 + HTML）**。因此代码会检查响应内容类型，把「回落成网页」与「接口报错」区分开——前者显示为在线并注明 `/ping` 未部署，不会被误判成代理故障。
- 未部署 `functions/ping.js` 时功能不受影响，只是状态行多一句「/ping 接口未部署」。

### 提示：hls.js 版本检查（5.1 新增，5.2 起仓库版本为 1.7.3）

`js/hls.min.js` 是**同源自托管的固定版本**，上游发布新版时不会自动更新。因此日志的「三、提示」会**每天检查一次**上游最新版本：

| 情况 | 提示内容 |
|---|---|
| 有新版本 | 橙色高亮卡片：`hls.js 有新版本：当前 1.7.3 → 最新 X.Y.Z`，并给出升级步骤 |
| 已是最新 | 灰色小字：`hls.js 版本 1.7.3（已是最新，检查于 09:42）` |
| 检查失败 | 灰色小字：`（更新检查失败：网络受限或接口不可达，明天自动重试）`——**不计入错误记录**，不污染日志 |

> 5.2 已把仓库内的 `js/hls.min.js` 从 1.5.7 升级到 **1.7.3**（上游当时最新版），并同步更新了 `log.js` 的 `HLS_BUNDLED_VERSION` 与 `index.html` 的注释版本号。1.7.x 的公开 API 与 1.5.x 完全兼容，`media.js` 用到的 `isSupported / Events / ErrorTypes / attachMedia / loadSource / recoverMediaError` 均未变化。

实现要点：

- **本地版本**取 `window.Hls.version`（hls.js 构建自带的静态属性）；若 hls.js 未加载，则回退到 `js/log.js` 里的常量 `HLS_BUNDLED_VERSION`。
  ⚠️ **升级时两件事都要做**：用新版覆盖 `js/hls.min.js`，并把 `HLS_BUNDLED_VERSION` 改成同一个版本号。
- **检查顺序**（任一成功即用）：
  1. 同源接口 `/hls-version`（`functions/hls-version.js`，服务端出口访问 npm 更可靠；KV 缓存 12 小时，每天最多 2 次写、若干次读）；
  2. `https://data.jsdelivr.com/v1/package/npm/hls.js`（取 `tags.latest`）；
  3. `https://registry.npmjs.org/hls.js/latest`（取 `version`）。
  未部署 `functions/hls-version.js` 时第 1 步会 404 并自动跳到第 2 步，功能不受影响。
- **一天一次**：结果写进当天报告（`r.hls`），所以反复切换页面不会重复请求，也不需要额外的节流逻辑。
- 该检查是一次**普通 `fetch`**（不是跨域脚本），失败静默处理，不影响页面与视频播放。

### 错误记录的覆盖范围

日志**并非**记录全部错误。为避免误判，覆盖边界如下。

**会记录：**

| 类别 | 实现方式 |
|---|---|
| 未捕获的 JS 运行时异常 | `index.html` 头部的「早期错误收集器」注册 `window` 的 `error` 监听 |
| Promise 未处理拒绝 | 同上，监听 `unhandledrejection` |
| **启动期错误**（关键依赖加载失败、各脚本顶层异常） | 收集器在所有脚本之前注册，先暂存内存，`log.js` 就绪后回灌，来源标记为 `启动期`。含 `hls.js` 加载失败（`<script onerror>` 上报） |
| RSS 订阅拉取失败 | `js/app.js` 显式钩子（带友好化文案 + 失败计数） |
| 媒体致命失败 | `js/media.js` 显式钩子（MP4 二次失败、HLS 致命且自愈用尽） |

**不会记录（截至 5.0 仍未覆盖）：**

- **图片 / 封面等资源加载失败**：`window` 的错误监听未启用捕获阶段，而资源错误不冒泡，因此抓不到；元素上的 `onerror` 只做代理回退、不写日志。
- **`console.warn` / `console.error` 输出**：代码中约 20 处 console 警告（如「RSS 代理返回了非 RSS 内容」「保存文章缓存失败：容量不足」「读取本地文章缓存失败」）只出现在 DevTools，不入库。
- **HLS 非致命错误与自愈过程**：`media.js` 中 `if(!data.fatal) return;` 直接返回；仅当自愈次数用尽才记 1 条。
- **被 `try / catch` 吞掉的异常**：凡代码自行兜住者不会冒泡（含日志自身写入失败）。
- **服务器端（Cloudflare Functions）错误**：`rss-proxy.js` / `media-proxy.js` 内部的失败、Cloudflare 自身 5xx 只在 Cloudflare 后台可见，浏览器仅能看到最终状态码。**因此详情里的「后台」指的是页面内异步过程（RSS / 媒体），不含服务端。**
- **被判定为「外部脚本噪音」的跨域 `Script error.`**：当 `hls.js` 已正常加载时，这类错误被确认为与本应用无关（详见下一节），**直接丢弃、不入库**。
- **应用未打开期间**发生的一切：跨天报告是下次打开页面时才创建的。

**关于跨域脚本的 `Script error.`**

`Script error.` 的字面含义是「某个**跨域脚本**内部抛了异常」——浏览器出于安全策略不会给出文件名与行号，只回传这一句。**自 5.0 起这类噪音已被自动忽略，不会出现在日志里。**

判定与处理（`js/log.js` 的 `recordError`）：

- 页面里唯一的跨域脚本曾是从 `unpkg.com` 加载的 `hls.js`，现已改为**同源自托管**（`js/hls.min.js`）。因此正常情况下**不再有跨域脚本**，也就不该再出现 `Script error.`。
- **忽略规则**：若消息以 `Script error.` 开头、且 `window.Hls` 已正常加载，则**直接丢弃不入库**——此时页面里所有脚本都已正常加载，被遮蔽的异常必然来自页面之外的脚本（浏览器扩展、国产浏览器 / 运营商注入），与本应用无关、也不影响功能。
- **唯一例外**：若 `hls.js` 本次**未能加载**（`window.Hls` 不存在），则仍会记录，文案形如 `Script error.（跨域脚本抛错，浏览器已隐藏详情；本应用 hls.js 本次未加载，请先确认是否有「依赖加载失败」记录）`，并按当天同文案折叠计数（`（当日第 N 次）`）。看到这条说明确有依赖缺失，需要检查。
- 判据：真正的跨域遮蔽表现为 `ev.message === "Script error."` 且 `ev.filename` 为空；若消息里带文件名/行号，说明是本应用自己的代码出错，会正常记录，不受忽略规则影响。

## 性能优化

当前版本针对较多订阅源做了基础优化：

- 打开页面时优先显示本地文章缓存
- 后台再检查 RSS 更新
- RSS 请求限制为分批并发，默认每批 `5` 个
- 滚动加载更多时只追加新卡片，不重绘已有卡片
- 手动刷新增加刷新锁，避免重复请求
- 自动刷新增加时间间隔，减少短时间重复加载
- **文章缓存 / 显示上限**：`js/core.js` 的 `ARTICLE_CACHE_LIMIT`（当前 `1000`，演变：600 → 800 → 1500 → 1000）。合并与缓存时按此上限截断，故列表总数不会超过它；超 `localStorage` 配额时按 `1000 → 800 → 600 → 400 → 200` 逐级降档保存，不会一次性砍到很小。注意 `localStorage` 总配额约 5MB，与 RSS 源缓存、运行日志共享，占用偏高时可先点日志页的「删除报告」腾出空间
- **RSS 源缓存条数限制**（`js/app.js` 的 `RSS_CACHE_ITEMS_PER_FEED = 120`）：RSS 源缓存与文章缓存是**两份独立副本**（同一批条目会被存两遍）。源缓存只用于「该源拉取失败时的回退展示」，故每个源只保留最新 `120` 条，避免源缓存体积与文章缓存相当、把 5MB 配额吃满
- **RSS 源缓存总预算**（`js/core.js` 的 `RSS_CACHE_TOTAL_ITEM_BUDGET = 900`）：除单源上限外再做一道全局预算，所有源缓存条目合计不得超过 `900` 条，超出则按「最旧优先」逐个删除源缓存；该检查带 30 秒节流，不会拖慢刷新

如需调整 RSS 并发数量，可以修改：

```js
const RSS_CONCURRENCY = 5;
```

如果订阅源较多但手机性能一般，建议保持在 `3` 到 `5` 之间。

## 部署说明（Cloudflare Pages）

1. Fork / 克隆本仓库到 GitHub
2. 在 Cloudflare Pages 新建项目，连接该仓库（构建命令留空，输出目录按 Pages 默认即可）
3. 配置 KV 命名空间 `RSS_CACHE`（**当前已实际使用**：作为 `/rss-proxy` 的服务端缓存，见下方「Cloudflare KV 的实际用途」）
4. 部署后，`functions/` 下的 Pages Functions 自动生效（按文件名自动注册为 `/media-proxy`、`/rss-proxy`、`/twitter-rss`、`/hls-version`、`/ping` 等路径），`_redirects` 负责把代理路径路由到对应 Function

> 注意：`functions/` 为 Cloudflare Pages Functions（非 Workers），共用同一运行时与 CPU 限制；媒体代理为纯流式转发，不做额外转码。
> KV 为**可选**绑定：未绑定时 `rss-proxy.js` 自动降级为实时代理，部署不报错、功能不受影响。

## Cloudflare KV 的实际用途

KV 绑定名 `RSS_CACHE`，被两个 Function 使用：`functions/rss-proxy.js`（缓存 RSS 原始 XML）与 `functions/hls-version.js`（缓存 hls.js 最新版本号）。

**① `/rss-proxy` —— 缓存 RSS 原始 XML：**

| 场景 | 行为 |
|---|---|
| 命中 KV | 直接返回缓存内容，毫秒级，不回源（响应头 `X-Cache: HIT`） |
| 未命中 | 回源拉取，成功后写入 KV，TTL **30 分钟**（`X-Cache: MISS`） |
| 回源失败 | 尝试返回 KV 中的旧数据兜底（`X-Cache: STALE`），保证可读 |

**② `/hls-version` —— 缓存 hls.js 最新版本号：**

| 场景 | 行为 |
|---|---|
| 命中 KV | 直接返回 `{version, source, checkedAt, cached:true}`，不回源 |
| 未命中 | 依次回源 npm registry → jsDelivr，成功后写入 KV，键 `hlsver:latest`，TTL **12 小时** |
| 上游不可达 | 返回 502 `{error}`；前端仅在「提示」里写「检查失败」，**不记为错误** |

免费额度（Cloudflare Workers 免费计划，每日 00:00 UTC 重置）与当前消耗：

| 项目 | 免费额度 | 本项目实际消耗 |
|---|---|---|
| 存储 | 1 GB | 约几 MB（各源最新一份 XML，30 分钟过期；外加 1 个版本号键） |
| 读取 | 100,000 次/天 | 每次刷新 × 订阅源数，量级很小 |
| 写入（不同键） | 1,000 次/天 | 每源每 30 分钟最多 1 次；版本号键每天最多 2 次 |
| 单值大小 | 25 MiB | 单个源 XML 通常几十到几百 KB |

> 结论：**1 GB 空间目前几乎没被用上**（用掉的是「缓存 XML」，不是「存条目」）。
> KV 是**服务端共享存储**，且最终一致（写入后最长 60 秒才全局可见）、写入量按次计费，
> 因此**不适合**直接替代浏览器 `localStorage` 存文章列表；若要做「大容量历史归档 / 跨设备同步」，
> 需新增服务端接口，属后续规划，当前版本未实现。

## 当前限制

- 数据只保存在当前浏览器，不支持多设备同步
- RSS 解析主要面向常见 RSS / Atom 结构，复杂源可能解析不完整
- m3u8 播放稳定性依赖源站和代理处理能力
- 自定义播放器为轻量实现，不包含倍速、清晰度切换等高级功能
- 本地缓存受浏览器 `localStorage` 容量限制（约 5MB，由文章缓存 + 来源缓存 + 运行日志共享）；可在「日志」页顶部查看实时占用与是否被降档

## 适合场景

这个项目适合个人自用，尤其适合：

- 聚合多个 RSS 图文源
- 聚合视频类 RSS
- 在手机浏览器中快速浏览订阅内容
- 不想搭建复杂后端或账号系统
- 希望保留本地化、轻量化使用方式
